## 1. Project name and overview

### Project name

HeatAtlas: Forecast Heat. Prioritise Relief.

### Overview

HeatAtlas (Forecast Heat. Prioritise Relief.) is a mobile-first web app that turns Pune's hourly heat forecast into a ranked map of neighbourhoods where heat hurts the most vulnerable people and relief (water taps, clinics) is scarcest. Volunteer leads get a ready-to-send dispatch brief; outdoor workers get the nearest verified water tap.

Scope (48h build):
- City: Pune, Maharashtra only. Bounding box 18.41,73.70 to 18.65,73.95, split into an 8x8 grid of 64 Heat Zones (about 3.3 km each, IDs Z-00 to Z-77).
- Live data only (Rule 4, zero mock data): Open-Meteo, WorldPop, OSM Overpass.
- Python/FastAPI computes every number (Eh, Vh, Rd). Google Gemini 1.5 Flash only handles natural-language voice/text intake, tool orchestration over the APIs, and writing structured dispatch briefs.

Form factor: responsive web app (React 18 + Leaflet + Tailwind CSS) designed for a 360 px phone first, with a FastAPI backend.

## 2. Problem statement

### Problem

- PAIN: Weather apps show one number for Pune ("40 C"). A delivery rider in Hadapsar and a street vendor in Kasba Peth get the same advice, although their heat stress, neighbours and nearest working water tap differ. Nobody tells outdoor workers and volunteers where the water taps, shaded stops and clinics are.
- IMPACT: Outdoor workers go hours without water or shade. NGO volunteer leads allocate water, ORS and cooling kits by guesswork, favouring familiar areas over the areas with the highest unmet need, while children and elderly residents in under-served zones carry the highest heat-illness risk.
- OUTCOME: Within 60 seconds of opening HeatAtlas, a volunteer lead sees the 3 zones with the highest relief deficit for the next 24 hours and can send a dispatch brief. A worker finds the nearest verified water tap in 3 taps or fewer.
- WHY GENAI: Volunteers speak or type free-form requests in English, Hindi or Marathi ("Send 2 teams to Yerwada this afternoon, we have 40 water cans"). Gemini converts that into structured intent, decides which data tools to call, and writes an actionable brief. Python computes all numbers, so the AI never invents a statistic.

### Live data sources (no auth, zero mock data)
1. Open-Meteo (10k calls/day): GET https://api.open-meteo.com/v1/forecast?latitude=18.5204&longitude=73.8567&hourly=temperature_2m,apparent_temperature,relative_humidity_2m&timezone=Asia/Kolkata . For zone-level data the backend sends one request with comma-separated zone centroids. Cached 60 min.
2. WorldPop v2 (1k calls/day): POST https://api.worldpop.org/v2/population with a GeoJSON polygon per zone, requesting total, child (0-14) and elderly (65+) counts. The adapter handles an asynchronous task-ID + poll response. Cached 24 h on disk (one full refresh = 64 calls).
3. OSM Overpass: GET https://overpass-api.de/api/interpreter?data=[out:json];(node["amenity"="drinking_water"](18.41,73.70,18.65,73.95);node["amenity"="clinic"](18.41,73.70,18.65,73.95););out; . One city-wide query, cached 6 h.

All caches hold only responses previously fetched from these live APIs. No seeded, hardcoded or fabricated data exists anywhere in the system.

### Sample request: POST /api/dispatch/brief

## 6. Processing rules and business logic

### Processing logic

### Zones and hours
- Hours_above_38C = count of hourly values in the window [start, end] where apparent_temperature > 38.0 C at the zone centroid. Default window is hours 0-23.
- Child_Pop = ages 0-14 and Elderly_Pop = ages 65+, from WorldPop.

### Deterministic formulas (Python only, never computed by the LLM)
Heat Exposure Person-Hours:   Eh = Population * Hours_above_38C
Vulnerable Person-Hours:      Vh = (Child_Pop + Elderly_Pop) * Hours_above_38C
Relief Deficit:               Rd = Vh / (Working_Water_Taps + 2 * Clinics + 1)

- Working_Water_Taps = OSM drinking_water nodes inside the zone, minus taps with 2 or more `dry` reports from distinct session tokens in the last 24 h that are not outnumbered by `working` reports.
- Clinics = OSM clinic nodes inside the zone.
- If Hours_above_38C = 0 then Eh = Vh = Rd = 0 and the tier is "No heat risk".
- Worked example, zone Z-34 with 7 hours above 38 C, Population 48,200, Child 9,100, Elderly 3,900, 6 working taps, 2 clinics: Eh = 48,200 * 7 = 337,400. Vh = (9,100 + 3,900) * 7 = 91,000. Rd = 91,000 / (6 + 4 + 1) = 8,272.7.

### Priority tiers (by Rd rank among zones with Rd > 0)
Critical = top 10% (deep red). High = next 20% (orange). Moderate = next 30% (yellow). Low = the rest (green). No heat risk = grey.

### Gemini 1.5 Flash tool-calling flow
1. POST /api/intake or /api/dispatch/brief sends the user's text or audio to Gemini (model ID from env var GEMINI_MODEL) with a system prompt and tool declarations.
2. Gemini returns function calls; the backend runs them against deterministic code and cached live data: get_forecast(zone_ids, start, end), get_population(zone_ids), get_relief_assets(zone_ids), compute_scores(zone_ids, start, end) returning Eh, Vh, Rd and tier, and get_nearest_assets(lat, lon, type). All tools are read-only.
3. Gemini receives the results and writes the brief as JSON: { summary, window, targets: [{zone_id, zone_name, tier, rd, vh, hours_above_38, recommended_action, assets_nearby}], resource_allocation, safety_note, language }.
4. Validator: every number in targets must equal the compute_scores output. On mismatch the backend overwrites it with the tool value; unknown zone_ids are dropped. After 2 failed schema validations the backend returns a template brief built purely from the scores.
5. Limits: max 6 tool-call rounds and a 20 s timeout per request.

### Uncertainty handling
Zones with missing population data are flagged population_unavailable and excluded from ranking. Stale cache age is always returned in the API response and shown in the UI.

## 8. Error handling and edge cases

### Error handling and edge cases

| # | Case | System Action | What User Sees |
| :--- | :--- | :--- | :--- |
| 1 | Open-Meteo unreachable or non-200 | Serve last cached live forecast if under 6 h old, otherwise return 503. Never substitute fabricated data. | "Live forecast unavailable. Showing data from 3h ago." or, with no cache, "Forecast unavailable. Retry." |
| 2 | WorldPop rate limit (429), timeout or pending task | Use the 24 h disk cache of earlier live responses; flag uncached zones population_unavailable and exclude them from ranking | Greyed zones labelled "Population data pending" |
| 3 | Overpass timeout or empty result | Retry once after 5 s, then serve the 6 h cache of the last live result | "Relief locations may be outdated" chip; with no cache, "Relief map unavailable. Retry." |
| 4 | Gemini fails, times out or returns invalid JSON twice | Build a template brief from the deterministic scores | Brief with a "Generated without AI summary" label |
| 5 | Audio too long, unsupported format, or silent | Reject with 422, or return an `unclear` intent | "Couldn't hear that. Try again or type your request." |
| 6 | Location outside the Pune bounding box, or permission denied | Skip distance sorting and show the city view | "HeatAtlas covers Pune only. Showing the city view." |
| 7 | Duplicate crowd report (same token, same tap, under 10 min) or invalid status | Ignore it and return 429 (duplicate) or 422 (invalid) | "Thanks, you already reported this tap recently." |
| 8 | Gemini output contains a wrong number or unknown zone | Validator overwrites numbers with tool values and drops unknown zones | The verified brief only; no error shown |

### Data rule: zero mock data (Hackathon Rule 4)
This overrides any generic instruction in this document to include demo, sample or seed data. The app must not ship mock, seeded or hardcoded weather, population or asset data. All data comes from the three live APIs above; caches store only earlier live responses. If a source is down and no cache exists, show an error state, not invented values.

### Privacy (zero PII)
- No accounts, names, phone numbers or emails are collected.
- Location is used only in the browser or per request for nearest-relief lookup and is never stored.
- Crowd reports store only osm_id, status, timestamp and a random session token, and are purged after 7 days.
- Audio is sent to Gemini only for transcription and is never stored on our servers.

### Safety and constraints
- Rate limit: 30 requests per minute per IP. API keys stay server-side.
- Medical disclaimer (shown in every brief and in the bottom sheet): "HeatAtlas provides planning information, not medical advice and does not replace IMD advisories. For heat stroke symptoms (confusion, fainting, very high body temperature) call 108 immediately."
- Gemini can only call the 5 read-only tools. The app must never dispatch emergency vehicles, send messages, or contact anyone automatically; sharing a brief always needs the user's tap.
- Gemini never computes or alters numbers; the validator enforces this.

## 10. Acceptance criteria and test examples

### Acceptance criteria and test examples

- AC1 Live forecast map: GIVEN the backend has network access, WHEN the user opens the app, THEN /api/zones returns 64 zones built from a live Open-Meteo response and the map shows coloured zones within 3 s on 4G.
- AC2 Timeline slider: GIVEN the map is loaded, WHEN the user drags the slider from +0h to +6h, THEN zone colours and the displayed apparent temperature update within 300 ms from cached data with no new network call.
- AC3 Deterministic scoring: GIVEN a zone with Population 48,200, Child 9,100, Elderly 3,900, 7 hours above 38 C, 6 working taps and 2 clinics, WHEN /api/zones/{zone_id} is called, THEN it returns Eh = 337,400, Vh = 91,000 and Rd = 8,272.7 (+/- 0.1).
- AC4 Dispatch brief: GIVEN the user submits "2 teams, 40 cans, 12-4 pm", WHEN /api/dispatch/brief completes, THEN the response is valid JSON in the documented schema, lists at most 5 target zones, and every Rd and Vh value equals /api/priority for the same window.
- AC5 Crowd verification: GIVEN a water tap with 0 reports, WHEN two different session tokens mark it `dry`, THEN the tap shows "Reported dry", is excluded from Working_Water_Taps, and the zone's Rd increases on the next request.
- AC6 Graceful degradation: GIVEN Open-Meteo is unreachable but a 2 h-old live cache exists, WHEN the user opens the app, THEN the map loads from cache with a "Showing data from 2h ago" banner and no error page appears.

### Test scenarios
- Scenario 1 (Worker): GIVEN a rider at 18.5284, 73.8739 with Overpass data loaded, WHEN they tap "Nearest relief", THEN the 3 nearest taps/clinics appear sorted by distance, each with a verification status.
- Scenario 2 (Hallucination guard): GIVEN a mocked Gemini reply with a wrong Rd value, WHEN the validator runs, THEN the final brief shows the compute_scores value, not Gemini's.
